## 设计意义

K1 已经发现"照搬 Phase 1 的压入上限则 1 N 不可达"，并加了一道加载期校验。K2 的过程证明那只是**三道天花板中的第一道**。三道互相正交，清掉一道不代表清掉另一道。

## 力控参数的三道天花板

| 天花板 | 条件 | 约束什么 | 检查位置 |
| --- | --- | --- | --- |
| 驱动钳位 | `max_press_speed × mass / output_dt ≥ F_target + tol` | 能不能**发出**足够大的命令 | `assess_force_reachability` |
| 积分权限 | `force_ki × force_integral_limit ≥ F_target × output_dt / mass` | 稳态下还能不能**维持**那个命令 | `assess_regulator_authority` |
| 比例稳定性 | `mass × force_kp / output_dt < 1` | 会不会**收敛**，还是持续振荡 | `assess_proportional_stability` |

### 第二道：积分权限

稳态时误差归零，比例项随之归零，命令速度必须由积分项独自供给，而积分项被 `force_integral_limit_ns` 钳住：

```text
要求  force_ki × force_integral_limit  ≥  F_target × output_dt / mass
实际  0.1      × 2.0                   =  0.2 m/s
需要  1.0 N    × (1/60) / 0.05         =  0.3333 m/s
```

继承增益下闭环的不动点：

```text
F = a(kp·T + ki·I_lim) / (1 + a·kp),   a = m/dt = 3 N per (m/s)
  = 3(0.2×1.0 + 0.1×2.0) / (1 + 0.6) = 0.75 N
```

1200 帧中落在 `±0.05 N` 内的帧数为 **0**，`regulate_force` 在 `regulate_timeout_s = 20 s` 处中止。

两点必须写清楚，否则会导向错误的修复：

- **`force_kp` 不在条件里。** 把不动点解 `F ≥ T` 会把所有比例项消掉。加大 `kp` 只抬高失败时停住的那个数，不会让目标变得可达。
- **0.75 N 出现了两次，是巧合。** Phase 1 的 0.25 m/s 压入上限恰好也对应 0.75 N，但那是 `frame_force_n` 在钳位处的值；这里的 0.75 N 是 PI 不动点，K2 的压入上限是 0.5 m/s，钳位并不是绑定约束。`binding_limit` 字段区分这两者。

修复按 K1 既有的推导惯例（`DERIVED_HEADROOM_FACTOR = 1.5`）：**只改 `force_ki` 一个值**（0.1 → 0.25），`force_integral_limit_ns` 与 `force_kp` 保持 Phase 1 取值不动。

### 第三道：比例稳定性

加入控制周期与反馈延迟的参数扫描后发现。单位命令速度产生的力是 `a = mass / output_dt`，在声明的一步反馈延迟下误差递推的齐次部分是 `-a·kp`，因此收敛条件为 `force_kp < output_dt / mass`。

**可用的比例增益与输出步长成正比。** 这一点容易漏掉，因为 `force_kp` 看起来像一个无量纲的调参旋钮，而且前面刚得出"kp 不约束可达力"的结论——它确实不约束可达力，它约束的是**能不能收敛**。

| 控制速率 | `a·kp` | 结果 |
| --- | --- | --- |
| 60 Hz（声明值） | 0.600 | 收敛到 `1.0000 N` |
| 120 Hz | 1.200 | 振荡，停在约 `0.50 N` |
| 240 Hz | 2.400 | 振荡，停在约 `0.30 N` |

实测边界恰在 `a·kp = 1`：`0.99` 仍收敛，`0.9999` 不收敛。因此允许值取边界的 `0.9` 倍，不贴边界。

### 第四道检查：实测驱动上限

前三道都是闭式推导。`F = mass × commanded_speed / output_dt` 对本 CPU 参考是精确的，但**只因为它省略的每一项在这里恰好都为零**：零线性阻尼、重力被精确抵消、每控制步一个子步、无求解器衰减。

把 `linear_damping_per_s` 设为非零值就能看出问题：

| `linear_damping_per_s` | 压入上限 0.5 m/s 实际产生 | 理想律预测 |
| --- | --- | --- |
| 0 | `1.5000 N` | `1.5000 N` |
| 5 | `1.3750 N` | `1.5000 N` |
| 10 | `1.2500 N` | `1.5000 N` |
| 30 | **`0.7500 N`** — 低于 1 N 目标 | `1.5000 N` |

这五个规格原先全部加载通过，静态检查全部报告可达 1.5 N。`linear_damping_per_s` 的裁决恰恰是 `enforced`——内核确实读它——所以这不是夹带了一个不支持的设置，而是一个**受支持但静态检查看不见**的设置。

`virtual_reality/authority_probe.py` 因此改为**问内核**：用真实配置跑真实求解器，按声明的压入上限施力，报告采样层实际报告的法向力。

报告显式列出**未覆盖**的内容：`feedback_delay_steps`、`force_kp`、`force_ki`、`max_correct_speed_mps`、`force_integral_limit_ns`。开环上限不是收敛结论，这部分由闭环扫描回答，**两者合起来才构成可达性主张**。

## 力反馈源

控制器读**采样后**的法向力，与层 2 发布、验收门槛评分的是同一个观测量。选这个而不是求解器原始值，是为了让控制器和它的门槛不可能对"力是多少"产生分歧。

采样阈值因此位于回路内部：被判为低于阈值的帧对控制器表现为无接触，于是调节器继续压而不是维持。

## 保持时长的验收语义

**比例不等于时长**：只保留沉降后 1 帧，带内占比仍是 `1.0`。原先的门槛只看占比，于是一次只保持了 `0.0167 s` 的运行可以通过声明为 `1 s` 的保持要求。

现在门槛同时要求时长：`held_frames ≥ ceil(hold_time_s / control_dt_s)`。

沉降帧**计入**保持时长。这不是任选的：控制器在锁定的那一帧就开始累加 `hold_elapsed_s`，所以锁定帧是第一个保持帧。门槛原先从锁定帧**之后**开始计数，比控制器实际保持的窗口少一帧——实测 59 帧对声明的 60 帧。

### 反证：不加这道校验会发生什么

临时绕过 `enforce_regulator_authority`、把 `force_ki` 改回 Phase 1 的 `0.1` 再跑：

```text
loop_state    aborted
abort_reason  force regulation timeout
frames        1405（其中 regulate_force 1200 帧 = 20 s 超时）
final force   0.750000 N
带内帧数      0 / 1200
是否进入滑动  否
```

没有加载期校验，这会表现为"力控门槛未通过"，**看不出问题出在规格本身而非求解器**。

## 稠密触觉场

复刻 Phase 1 Step 6.4 的 13 通道布局，通道名与顺序完全一致，既有消费者无需改动即可读取。

```text
dense_contact_field.npz   shape = (797, 64, 64, 13)   float32
时间轴帧数 797 == 控制步数 797
```

**时间轴取自控制步，不取自 cell 记录。** 稀疏行只在有接触时存在，仅凭它建时间轴会悄悄丢掉 `pre_contact` 与 `released`——而"释放后接触力清零"的证据恰恰在那 30 帧里。门槛显式校验这两段存在。

逐格比对（`dense_field_matches_sparse_cells` 门槛）：

| 检查 | 结果 |
| --- | --- |
| 帧数 == 控制步数 | 通过 |
| 无接触段保留 | 通过 |
| 未映射的稀疏 cell | 0 |
| 稀疏记录里没有的稠密 cell | 0 |
| `patch_id` 不一致 | 0 |
| 单格力最大误差 | `3.0e-8 N`（float32 存储精度，非求解器精度） |

另以 `cells.csv` 独立复算：447 条稀疏行 ↔ 447 个稠密激活格，力之和 `369.430758` 对 `369.430756`，`released` 段力之和恰为 `0.0`。

**一处对 Phase 1 的有意修正。** Phase 1 在曲率或方向无效时写 `0.0`，使"未定义"与"平坦"、"未移动"无法区分——正是本仓库在别处禁止的伪造零。13 通道布局为兼容保持不变，但有效性标志作为独立的 `[T,H,W]` 布尔数组 `curvature_valid` / `direction_valid` 随张量一同存储。

**稠密化只改变存储布局，不提高空间精度，不把代理面积变成物理面积。**

## 曲线报告

`contact_report.html`，单文件、离线可开、无外部资源、无脚本。四张图：探头高度与法向命令速度、法向力与调节带、切向速度、接触单元数与占格代理面积。

用内联 SVG 直接从运行数组生成，**不新增绘图依赖**——仓库依赖仍只有 `jsonschema` 与 `numpy`，尤其因为这个报告必须能在无显示器机器上生成。

两处诚实性处理：

- **数据缺口断线，不跨接。** 无接触帧没有力，跨过它连线会画出一段运行从未产生的直线，**图会断言数据所否认的连续性**。
- **调节带画的是门槛评分依据的那条带**，取自 `controller.force` 的声明值，不是重绘的近似。
