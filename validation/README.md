# Validation

该目录存放契约验收、跨后端趋势比较和 Phase 2 退出条件。比较报告需要同时记录原始证据、标准状态、指标定义和不可比较字段。

`k1_acceptance.py` 实现 K1 的九项门槛。所有阈值取自规格的 `acceptance` 块，不在验收代码里写死数值。

| 门槛 | 读取对象 |
| --- | --- |
| 运行完成所声明的程序 | 单轮运行 |
| 单探头接触出现 | 单轮运行 |
| 保持阶段接触稳定 | 单轮运行 |
| 受控段接触覆盖率达标 | 单轮运行 |
| 滑动速度达标 | 单轮运行 |
| 释放后接触力清零 | 单轮运行 |
| 总力与冲量一致、Point 到 Cell 到 Patch 守恒 | 单轮运行 |
| 时间步变化不改变数据语义 | 仅子步不同的多轮运行 |
| `InteractionState` 完整回放 | 写好的运行目录 |

## 阈值台账

指标算了、对着阈值打印了、但没有人比较——这是冻结前发现并修掉的一类缺陷。结构性防线是两张台账：`ACCEPTANCE_KEY_GATES` 记录每个声明阈值由哪个门槛消费，`DEFERRED_ACCEPTANCE_KEYS` 记录显式延后到哪个里程碑。有键落在两者之外时 `acceptance_key_ledger` 直接报错，因此后续阶段新增阈值无法被静默忽略。

## 两种结论

最后两项门槛需要单轮运行之外的输入，因此报告分开给出两种结论：`run_checks_passed`（七项单轮门槛全通过，这是只传一个运行能确立的全部）和 `k1_acceptance_passed`（九项全部发出且通过，需要两个不同物理步长的细化运行与一个已写出的运行目录）。`all_passed` 即后者，因此省略这些输入的调用方无法把结果读成完整通过。

时间细化要求至少两个不同的 `substeps_per_control`：把同一个运行当作自己的对照没有改变时间步，证明不了任何事。

所有结论由唯一的 `finalize_report` 计算。调用方追加门槛（例如只能在清单落盘后验证的回放门槛）后必须经它收口，而不是自己写一遍 `all(gate["passed"] ...)` —— 那种写法会静默丢掉完整性要求。

第 5 项的语义指段序列、接触与释放序列、帧数、Cell 与 Patch 身份、守恒等式。力的量级依赖驱动语义，因此报告实测离散，不假定与步长无关。

第 6 项在清单写完之后验证：哈希绑定的文件不能包含关于自身哈希的已验证结论，所以它单独写入 `replay_check.json`。
